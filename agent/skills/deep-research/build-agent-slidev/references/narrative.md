# Narrative, storyboarding, and information design

Primary capability context: <https://sli.dev/guide/why.html>. The editorial practices below are skill guidance, not Slidev CLI requirements.

## Start with the change

Complete this sentence: **“After the talk, [specific audience] should understand / believe / do [one thing].”** Choose three supporting ideas at most for a short talk. Define the audience's starting knowledge, objection, and desired next step. A developer explanation, a persuasive keynote, and a hands-on workshop should not share the same story or density.

| Setting | Bias toward | Avoid |
|---|---|---|
| Keynote | Bold premise, paced reveals, evidence, emotional closure | Tiny documentation, dense dashboards |
| Technical deep dive | Mental model, executable/code evidence, explicit caveats | Long tutorials on one unreadable slide |
| Workshop | Chapters, short instruction steps, checkpoints, recovery notes | Unrehearsed live setup or unexplained jumps |
| Executive/decision | Recommendation first, quantified alternatives, risks, decision ask | A chronological account of implementation |
| Report/reference | Readable detail, navigation, citations, searchable exported artifact | Unnecessary click-only content |

## Storyboard in plain text first

For each planned slide, write:

| Number | Job / one-sentence promise | Evidence or visual | Click beats | Notes / time |
|---|---|---|---|---|
| 1 | Why this matters now | Concrete contrast | 0 | 30 s |
| 2 | The model in one picture | Diagram / minimal code | 2 | 60 s |

Mark each slide's **job**: hook, orient, explain, prove, demonstrate, contrast, transition, summarize, or ask. If two jobs compete, split the slide. If no job exists, delete it. Do not let a feature search replace the story.

A robust arc:

1. **Promise:** a surprising result, question, or audience problem—not just a logo.
2. **Context and stakes:** enough background to care, with an explicit scope.
3. **Mental model:** a diagram, analogy, or before/after that makes later detail understandable.
4. **Proof / demonstration:** code, data, process, or example; claim followed by evidence.
5. **Tension:** tradeoff, failure mode, comparison, or misconception.
6. **Application:** what the audience can now do or decide.
7. **Close:** one durable thought and an action; not an accidental blank `end` slide.

Section dividers should signal a meaningful change of thought. Use a recurring “where we are” visual for longer talks, not a table of contents repeated after every few slides.

## Click choreography and timing

A click is a rhetorical beat: reveal a consequence, focus attention, compare states, or let a question land. Write it in the storyboard before implementing. Avoid accidental clicks generated by nested directives, multiple independent lists, and invisible code states.

Plan a timing range rather than pretending the talk has an exact duration. Reserve 10–20% spare time for interaction and transitions. Deliberately rehearse the longest code/diagram slide and all click sequences. For workshops, add explicit exercises and buffers to the deck itself.

## Content without hallucination

- Preserve the user's evidence and wording when fidelity matters.
- Put a concrete claim near its supporting chart, example, or source.
- Use real URLs and label dates; sourced metrics need useful context, not decorative precision.
- Never make a fake browser screenshot, fake analytics curve, or unsourced quotation look real.
- Mark placeholders with `TODO [needs owner/source]` and do not call such a deck finished.
- Explain the diagram aloud in notes; a complex picture without a message is editorial noise.

## Final-state and fallback review

Read the deck with all clicks complete. Does it stand alone in a PDF without the presenter? If yes, notes can be minimal; if no, export a companion handout or record explanatory notes. For network demos, prepare local screenshots and a verbal summary. Decide whether pacing or readability matters more for each output; the browser deck and handout may need different export options or source branches.
