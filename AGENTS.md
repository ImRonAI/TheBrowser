# AGENTS.md — Ron Browser Rebuild

Guidance for AI coding agents working in this repository. Assume the reader knows nothing about the project.

## Project overview

**Ren** is a local-first, agentic desktop browser (the repository, code, routes and storage keys predate the name and keep the `ron` spelling; see *Brand: Ren*). It combines:

- an **Electron** main process (`electron/`) that owns native browser tabs (`WebContentsView`) and embeds browser automation via the sibling package `electron-playwright-mcp` (a `file:../electron-playwright-mcp` dependency — `npm install` fails without that checkout);
- a **React 19 + TypeScript renderer** (`src/`) that acts as the browser chrome (tab bar, URL bar, agent panel, projects/issues boards, onboarding);
- a **Python FastAPI backend** (`agent/api/`, "Ron Browser API" v4.0.0) built on the **commit-pinned Strands Python SDK** (`deploy/prepare-strands.sh`), which owns all agent sessions, tools, providers, and streaming.

The three processes run separately and communicate over localhost HTTP/SSE. There is also a 24/7 VPS deployment (`deploy/`) where the backend and a headless Electron "cloud browser" run under systemd and the Mac reaches them over an SSH tunnel.

### Ports

| Port | Process | Purpose |
|---|---|---|
| `8765` | FastAPI (`agent/api/main.py`) | Agent Panel chat, sessions, SSE, models, projects, articles |
| `3000` | Electron main | Electron control surface for `electron-playwright-mcp` |
| `8931` | Electron main | Playwright MCP HTTP surface |
| `9222` | Electron main | CDP (Chrome DevTools Protocol) |
| `13000`/`18931`/`19222` | SSH reverse tunnel | The Mac's Electron browser as seen from the VPS (`user` browser target) |

The Vite dev-server port can drift; CORS allows any `localhost`/`127.0.0.1` origin by regex.

## Commands and setup

- Use `venv/`, not `.venv/`; npm scripts and Pyright target it. Python dependencies come from `agent/api/requirements.txt`.
- Before installing Python requirements, run `bash deploy/prepare-strands.sh` from the repo root. It clones GitHub directly into `agent/api/core/harness-sdk` at `563f57d7a387931760a2c3106014cd7c0db4c9bc`; requirements install its full Python package editable. The clone is ignored and reconstructed with `deploy/strands-bidi.patch`. Never copy files from the sibling BidiAgent checkout or prepend its path to `sys.path`.
- `npm install` requires the sibling `../electron-playwright-mcp` package (`file:` dependency).

```bash
npm run electron:dev   # kills stale dev listeners (never the SSH tunnel), then Electron; agents on VPS :8765 when tunneled; optional local Python on 8766 for Live if VPS lacks /bidi
npm run dev:vite       # Electron/renderer only; kills :3000/:8931/:9222 unless RON_DEV_SKIP_PORT_KILL=1
npm run dev:backend    # local API only on 127.0.0.1:8765 (API_HOST/API_PORT override); prefer electron:dev so VITE_* matches
npm run build          # dist/electron + dist/renderer
npm run start          # built Electron app
npm run typecheck      # tsc --noEmit
./venv/bin/python -m pytest agent/tests -q
./venv/bin/python -m pytest agent/tests/test_chat.py::test_health
node --experimental-strip-types --test src/lib/panel-stream.test.ts   # renderer tests
shellcheck deploy/*.sh deploy/local/*.sh
```

- Manual Electron launches require `unset ELECTRON_RUN_AS_NODE`; the npm scripts handle this.
- `npm run electron:dev` (`deploy/local/electron-dev.sh`) probes `localhost:8765` and sets **`VITE_API_BASE_URL`**, **`VITE_LIVE_API_BASE_URL`**, and **`VITE_SEARCH_API_URL`** (only when needed). With the SSH tunnel up, **8765 is the VPS** — panel, discover, **search**, projects, memory, and (after deploy) live/teaching all use that origin unless a route is missing and a **8766** sidecar is started. **Do not** pin `VITE_*_URL` in `.env.development.local` (it overrides the script and causes dead-port 404s). Built apps default to `http://localhost:8765`. Guest issue API pinning (`ron-project-api-url-v1`) remains authoritative when set.
- Pyright is not installed in `venv/`; use `npx -y pyright@latest <files>`. `panel_agent.py`, `panel_tools.py`, and `chat.py` carry pre-existing pyright errors — compare error sets against the previous commit rather than requiring zero.

- Key Python pins: Strands source SHA above with `a2a,mistral,openai,anthropic,gemini,bidi-google` extras, `supabase==2.31.0`, `strands-harness==0.1.2`, `strands-agents-evals==1.4.0`, `strands-xai==0.6.1`, `perplexityai==0.43.5`, `mcp==1.26.0`, `openai==2.50.0`, `anthropic==0.76.0`, `google-genai==2.24.0`, `pydantic==2.12.5`, `huggingface_hub==1.20.1`, `playwright==1.57.0`, `a2a-sdk==0.3.22`.

## Runtime architecture and boundaries

These boundaries are load-bearing; do not casually cross them. `docs/panel-runtime.md` is the pinned authoritative reference.

- **Panel controls**: goal, background tasks, tool execution, context and checkpoint settings are prompt slash commands (`src/lib/panel-commands.ts`), not a header settings form. Commands only configure existing native Strands options before the first message; an existing session's options remain immutable. Checkpoint UI uses the existing AI Elements checkpoint component and resumes via `checkpoint_resume`. The panel agent's **Teach Ron** trigger is in `ChromeToolbar`, beside the panel toggle, so closing the panel does not unmount its teaching studio.

- **Skill teaching** (`agent/api/core/teaching.py`, `core/process_document.py`, `endpoints/teaching.py`, `endpoints/teaching_observe.py`, `src/components/agent-panel/TeachSkill.tsx`): each panel destination and issue agent owns its learned skills. Teach Ron is one native `BidiAgent` (`gemini-3.8-live` by default, see Voice / Gemini Live) seeded with the brief (`title`, `objective`, `context`) and prior journal; the active browser tab (or the window beside the studio, for an internal page) streams at most one JPEG per second through native `RealtimeInput` video. It is seeded with the learning SOP (`agent/sops/learning-a-new-skill.sop.md`, phase `observe`) from the upstream Agent SOP MCP server, runs only on `gemini-3.8-live` (Extended Thinking never emits the `journal` call and is refused with `invalid_settings`), receives frames, voice and notes as-is with no injected turns (the former `RON_TEACHING_TICK_SECONDS` observation tick made the audio model narrate every click and was removed 2026-10-09). **What is taught is the outcome, not the clicks**: the observer prompt and SOP tell Ron it will later produce the same result faster with its own tools (`http_request`/search over browsing, browser only where no API exists, shell/editor, `environment` for secrets, `render_ui` for an interactive result the user can rate, `add_memory`/`search_memory` so feedback shapes the next run). The lesson has two parts in one Live session: **demonstrate** (silent: journal what the user wants, which sources, what they pick/skip and why, how they judge success; speak only when addressed) and **debrief** — the studio's *Finish demonstration* sends `{type:"finish_demo"}`, the server stops accepting frames, emits `{type:"debrief"}` and sends `DEBRIEF_REQUEST` once; Ron then speaks: (1) its understanding of goal/inputs/decisions/success, asks if right, applies corrections; (2) every remaining question, one at a time; (3) its implementation plan (tools reused, what is new, the `render_ui` view and its controls, the memory topic), asks for agreement; journal entries written after `finish_demo` are kind `debrief`/`debrief_user_speech`/`debrief_assistant_speech` and the reviewer treats them as authoritative over observations. There is **no timer during the debrief**; *End conversation* sends `{type:"stop"}`, which asks for `finish_observation` and arms `RON_TEACHING_STOP_GRACE_SECONDS` (20) as the backstop; the server then sends `{type:"stopped", finished}` and closes. `LessonLog` (native `OutputStream`) logs every lesson's SOP load, tool calls/results, journal appends, transcripts and outcome counts. It journals with its **own copy** of the `journal` tool (`core/teaching_journal.py`, same `write/read/list/add_task` semantics as `agent/tools/strands_tools/devops/journal.py`, bound to the lesson workspace, no cwd/env), mirrored into `TeachingService.append_journal` together with auto-journaled user/assistant speech; it must never modify existing tools or skills — `copy_into_lesson` plus `LessonWorkspacePolicy` (native `BeforeToolCallEvent` cancel: editor writes only inside the workspace, `shell`/`environment`/`mcp_client` denied because there is no sandbox) make authoring copy-only. Start captures that browser view, then requests microphone and camera permission; the camera is composited as a small circle at the bottom right of the model's frame. The studio is a full-height side panel the same width as the agent panel. `/finish` prepares an escaped HTML process review only: the reviewer discovers capabilities read-only (`tool_catalog` list/search/describe, `list_learned_skills`, `list_harness_agents`, A2A discovery) and records the most efficient implementation (`implementation`) and open `questions`. Review, publish and SOP children run on a native `ModelRouter(FallbackStrategy)` (`teaching_model`: Gemini, then `RON_TEACHING_FALLBACK_MODELS` via Perplexity) with native `structured_output_model`. Publish may create a specialist with `create_harness`; after publication the skill is demonstrated once through its own SOP (`session.demonstration`). `/review` requests corrections; `/approve` binds human approval to the exact revision and journal digest before generating `SKILL.md`, `workflow.sop.md`, actual references/scripts and `tool-group.json`. Native SOP source is the pinned `strands-agents/agent-sop` GitHub package: `core/native_sop.py` starts its unmodified MCP server and retrieves the workflow prompt. One native Agent follows the ordered natural-language SOP with the approved tools; this is not a custom deterministic step runner. The teaching studio keeps capture alive when minimized; closing stops it. FastMCP is mounted at `/skills/mcp/` with its lifespan and exposes `get_tool_group` plus skill discovery/read/execution. Generic MCP execution rejects issue scopes; only the authenticated issue agent can bind its own tools. Taught-skill memory is durable even when panel conversations are ephemeral. Issue history returns `owner_id` so guest capabilities never appear in teaching URLs. These trusted-loopback host-execution surfaces must never be added to the ngrok allowlist. See `docs/skill-teaching.md` for contract and verification limits.

- **Session ownership / threads**: `PanelRuntimeManager` owns one live agent per user/session and server-owned invocations. Default storage is ephemeral; `PANEL_STORAGE=huggingface` enables HuggingFace Buckets. Run one writer process. Do not replace SDK execution or snapshot implementations. A **thread** is one `session_id` opened by **two agents**: the Chat `Agent` and the Live `BidiAgent`. Both construct with the same native key — `thread_agent_id(user_id)` + `ThreadSessionManager` (`core/panel_storage.py`: a `SnapshotSessionManager` subclass whose only override is `_capture` = `take_snapshot(preset="session")`, so the **system prompt stays with the agent, not the thread**) over `get_user_session_storage(user_id)` — so the SDK restores the thread's `messages`/`state` on construction (`AgentInitializedEvent`) for either kind. Live saves on every `MessageAddedEvent`/`MessageUpdatedEvent` (`bidi_agent_save_latest_on="message"`, SDK default) and checkpoints on `BidiAgentStopEvent`; Chat uses the runtime's `save_latest_on="trigger"`. **Live-verified 2026-10-07 on `gemini-3.8-live`**: a fresh `BidiAgent` on the same session restored 6 messages and recalled the fact (the SDK docs' "not persisted across restarts" note for Gemini Live is out of date for the pinned source). The renderer bridges **nothing** between Chat and Live (no `liveHistory`, no `LiveTurnsReadOnly`, no Live `context.history`); `/bidi?session_id=` (older `conversation_id` alias) opens the thread and `ready.history_source="snapshot"` + `restored_messages` report the native restore. **Takeover** (`core/live_takeover.py`, the only custom piece: the trigger): when a Live socket ends (`WebSocketDisconnect`, Live failure, window closed, sign-out) and `pending_work(agent.messages)` — the thread ends on a user turn, a `toolUse` without result, a `tool_result` without an assistant conclusion, or a `pending`/`incomplete` bidi block — `endpoints/bidi.py` calls `PanelRuntimeManager.start(user_id, session_id, TAKEOVER_PROMPT, selection={…, browser: "cloud"})`: the Chat agent restores the same native session and finishes the work on the cloud browser (the user's browser is gone by definition); the `[handoff]` prompt is a durable user message so the thread shows when/why. `RON_LIVE_TAKEOVER=0` disables. The takeover run is **unattended**: `chat._create_runtime_agent` adds `UnattendedRunGuard` (native `BeforeToolCallEvent.cancel_tool`) whenever the selection is pinned to `cloud`, so `ask_user` and the fixer hand-off (`a2a_send_message` to `/a2a/fixer`, which needs HITL approval) are cancelled with a note and the agent ends with a summary instead of parking the thread `interrupted`; `TAKEOVER_PROMPT` scopes the run to the user's last request only. Chat's context is the SDK's: `ContextOffloader` (oversized tool results on the session storage, read back with `retrieve_offloaded_content`) and `SummarizingConversationManager(preserve_recent_messages=4, proactive_compression=True)` against the model's real window (see *Seamless agent respawn*). The summary is produced by a fresh `Agent` on the panel model — the SDK deadlocks if the panel agent summarizes itself — and written back into this thread's session. That is what keeps a bidi-written history (two `toolUse`/`toolResult` pairs per tool group, `loop.py:664-688, 755-764`) within budget — there is no custom history normalizer. **Threads read model** (`core/threads.py`, `supabase/migrations/014_threads.sql`): `ThreadProjection` is a native `HookProvider` on both agents (`MessageAddedEvent`/`MessageUpdatedEvent` debounced, `AfterInvocationEvent`/`BidiAgentStopEvent` flush) that mirrors `agent.messages` into `threads` (`session_id, destination, title, last_agent chat|live, browser, message_count`) + `thread_messages` (`seq, role, kind user_prompt|assistant_output|reasoning|tool_call|tool_result, agent, content`) under owner RLS; guests are never projected. `GET /sessions?user_id=` lists, `GET /sessions/{id}/thread` reads in order; renderer `ThreadsList.tsx` (header Threads button) opens any thread in the current view via `usePanelChat.openThread`. Tests: `test_live_takeover.py` (pending_work, selection, trigger, **bidi→Agent native restore round trip** with a scripted `BidiModel`), `test_threads.py`, `src/lib/threads-api.test.ts`.
- **Seamless agent respawn: stalls, timeouts, context overflow** (`panel_runtime.py` `_execute`/`_respawn`/`_recover_if_stalled`, `panel_agent.TimeoutRetryStrategy`, `core/context_windows.py`, knobs in `config.py`, wired in `chat.create_runtime_manager`; contract `docs/panel-runtime.md` § Recovery): recovered **inside the same run** — no `error` envelope, no new run, nothing stored in the thread. **No failure closes a session** (`recovery_required` is always `false`): the runtime's `ThreadSessionManager` uses `save_latest_on="message"`, so `snapshot_latest` holds every completed message; a run active when the process stopped is continued under the same `run_id` on the first access in the next process (`_load` → `_resume_interrupted`, fresh agent, native restore, `[]`), and a failed run drops its instance so the next message builds a fresh agent on the same session. **Stall**: one loop-local watchdog (first `start()` starts it, `shutdown()` cancels it) refreshes a per-run activity clock on every emitted event; a `starting`/`running` run silent past `PANEL_RUN_STALL_SECONDS` (default **120**; `0` disables) is stalled, except a tool call in flight (ids from their deduplicated `tool_input` to `AfterToolCallEvent`), which gets `PANEL_RUN_TOOL_STALL_SECONDS` (default **480**, above song generation's 420s); the watchdog cancels only the current stream attempt (`_attempt_task`). **Timeout**: `TimeoutRetryStrategy` = native `ModelRetryStrategy` with its documented `is_retryable` extended by `is_model_timeout` (`TimeoutError`, httpx timeout, gRPC `DEADLINE_EXCEEDED` on the cause chain); one that outlasts the native backoff reaches the runtime. **Overflow**: the conversation manager compresses proactively at `PANEL_CONTEXT_COMPRESSION_THRESHOLD` (0.87 of the model's real window, the SDK's `compression_threshold`); on a real overflow the SDK first runs `SummarizingConversationManager.reduce_context` (`preserve_recent_messages=4`, the SDK's `overflow_protection` floor; the default 10 left a single tool-heavy turn "Cannot summarize: insufficient messages") and only an unreducible overflow reaches the runtime. **Recovery** (`_respawn`, run inside the cancellable attempt so a hung disposal/factory is recovered too; ≤ `PANEL_RUN_MAX_RECOVERIES` = **2** consecutive, reset by every completed tool call, stored in the journal so restarts count): save the old instance as `snapshot_latest`, dispose it (bounded flush/cleanup), build a fresh agent from the same factory on the same `ThreadSessionManager` (native restore → same conversation manager, `ContextOffloader`, `ContextInjector`, tools), continue with `[]` (the SDK closes an unanswered `toolUse` with its own "Tool was interrupted."; the runtime emits that `tool_result`); one `retry` event with `silent: true` makes the renderer discard the failed attempt's partial text without a retry line (`XAIStatePruner`'s overflow retry is silent too); the `ContextInjector` adds an ephemeral `[recovery]` note to later calls; after an overflow the request's browser context is cut to `RECOVERY_CONTEXT_SHARE` (25%) of the model's real window. A stall, timeout or overflow past the budget, or startup I/O silent for a whole window, fails the run with that error like any provider error; the session stays open. `_reserve` restarts the activity clock (a message sent more than a stall window after the previous run's last event used to be cancelled during startup). **Real context windows**: `build_model` sets `context_window_limit` from provider metadata (`context_windows.provider_context_window`: xAI `GET /v1/models` `context_length`, Mistral `max_context_length`, Gemini `inputTokenLimit`, Perplexity `<vendor>/` ids via that vendor; OpenAI/Anthropic publish none, so the SDK table applies; failures logged, not cached; tests force a failing `HTTP_TRANSPORT` in `conftest.py`). Tests: `test_panel_runtime.py` (`test_context_overflow_respawns_*`, `test_stall*`, `test_model_timeout_*`, `test_timeouts_*`, `test_no_recovery_*`), `test_context_windows.py`, `test_xai_model.py`, `src/lib/panel-stream.test.ts`.
- **Harness builtin plugins on the panel agent** (`panel_agent.create_panel_agent`): `Todos` (`PANEL_TODOS`, default on) vends `todo_write`, keeps the list in `agent.state` (session-snapshot-persisted, re-injected before every model call) so a respawned instance resumes its plan; `EnvironmentContext` (`PANEL_ENVIRONMENT_CONTEXT`, default on) injects platform/date/cwd/AGENTS.md before each user turn; `PANEL_INTERVENTIONS` (default off — an approval gate parks unattended runs) resolves the strands_harness sugar (`"ask"`/`"smart"`/policy/`.cedar`) onto native `Agent(interventions=...)`. Tests: `test_panel_composition.py::test_harness_*`.
- **SSE protocol**: the panel uses versioned, session-sequenced application envelopes (`{version: 1, sequence, session_id, run_id, type, node_path}`), not raw SDK or AI SDK UI streams. Keep `agent/api/core/panel_runtime.py`, `src/lib/panel-stream.ts`, and `src/components/agent-panel/usePanelChat.ts` synchronized. `POST /chat` returns the SSE stream directly; `GET /sessions/{id}` is the canonical snapshot; `GET /sessions/{id}/events?after=<seq>` replays; `/steer` and `/cancel` control runs.
- **Agent composition**: agents are built with `strands.experimental.config_to_agent` (accepts only `name`, `model`, `prompt`, string `tools`) plus constructor overrides for provider instances, managers, plugins, and callbacks. A bare model string selects Bedrock. Providers: NVIDIA NIM, Perplexity, Mistral, xAI, Gemini, OpenAI, Anthropic (`PROVIDERS` in `panel_agent.py`). `RON_CHAT_PROVIDERS` (comma list of those ids; unset = all; the local `.env` sets `nim,mistral`) limits which are offered to chat: `chat_providers()` feeds `configured_providers()` (so `/models`, defaults and the Live takeover), `/config.providers` lists only offered providers (the picker hides the rest), and `/chat` / `/models/{id}/efforts` answer 400 for any other; Live (`/bidi`) keeps `GEMINI_API_KEY` regardless. Preserve `stream_async`. Preserve `perplexity_model.py`'s complete function-argument recovery. Server-side tools belong in provider configuration, distinct from `Agent.tools`.
- **Tools**: keep `agent/tools/strands_tools/` off `sys.path` (it shadows the installed `strands_tools` distribution). `tool_catalog` imports library files as `ron_vendored_tools.<category>.<module>` (synthetic package, so relative imports resolve) and publishes them at the `AfterTools` boundary. Core tools (`mcp_client`, `editor`, `shell`, `environment`, `http_request`, `perplexity_search`, `tool_catalog`, `ask_user`) come from installed `strands_tools`/vendored `@tool` modules and run on the host; there is no shell sandbox or Shell MCP. Those installed tools gate mutating actions behind a prompt_toolkit `[y/*]` stdin confirmation; the API has no TTY, so `core/config.py` sets `BYPASS_TOOL_CONSENT=true` at import (`RON_TOOL_CONSENT=prompt` opts out) — without it every `shell`/`editor`/`environment`/non-GET `http_request` call fails with `[Errno 22] Invalid argument` in every agent. The same block sets `PAGER=cat`, `GIT_PAGER=cat`, `GIT_EDITOR=true`, `GIT_TERMINAL_PROMPT=0`: `shell` runs every command in a PTY, so `git log` would otherwise open a pager and hang until `SHELL_DEFAULT_TIMEOUT` (900 s). ## Security considerations

- **Sign-in entry point**: guests get a toolbar **Sign in** button (`UserMenu.tsx`; signed-in users get the avatar menu with Sign Out) and the music deck's own Sign in buttons; all go through `src/lib/sign-in.ts` (`openSignIn()` sets `#signin`, which `App.tsx` renders as `SignInPage` with `onContinueAsGuest`, and clears automatically once `isAuthenticated`). `isGuestUserId` (`default`, `guest:*`, `dev-user`) is the renderer's guest test — the former SignInPage dev bypass that faked a `dev-user` account was removed because it passed renderer checks but failed every owner-scoped backend call. Email+password and sign-up hit the live Supabase project; OAuth is below.
- **Music deck visibility**: `shouldShowMusicDeck` (`liveMusicStore.ts`) — the deck mounts only when a Lyria session is connected/playing/paused, a recorded take awaits save/discard, or there is a music error; a Live session that merely *could* play music shows nothing. Guests see the prompts and a Sign in button; transport/save stay disabled.
- **Social sign-in (desktop OAuth)**: `loginWithOAuth` asks `electron/main.ts` for a one-shot loopback URL (`http://127.0.0.1:<port>/auth/callback`, RFC 8252 §7.3), calls `signInWithOAuth({ skipBrowserRedirect: true, redirectTo })`, leaves the sign-in screen, and opens that https URL as a Ron tab (`tabs.create` + `switch`). Provider `window.open` popups already become tabs (`setWindowOpenHandler`). The loopback listener relays the callback as `deep-link`; the renderer exchanges the code and closes the sign-in tab. **Google and GitHub do not see the loopback URL.** Probed 2026-10-15: `GET /auth/v1/authorize` on project `goyzjhwgstvmgaykmnwi` 302s to each provider with `redirect_uri=https://goyzjhwgstvmgaykmnwi.supabase.co/auth/v1/callback`. Google answers `redirect_uri_mismatch` (`flowName=GeneralOAuthFlow`) and GitHub answers "The redirect_uri is not associated with this application" because that exact callback is not registered on the OAuth client configured in the Supabase dashboard (Google: Web client, Authorized redirect URIs; GitHub: OAuth App, Authorization callback URL). Registering the loopback URL on Google or GitHub does not fix it. After the provider accepts, Supabase redirects to the loopback URL only if it is allowed — the dashboard needs `http://127.0.0.1:*/auth/callback` (Authentication → URL Configuration) or it falls back to the Site URL silently. `authStore.loginWithOAuth` reports `OAUTH_TIMEOUT` after 3 minutes without a callback. Microsoft (`azure`) is not enabled on this project.

- Secrets (provider API keys, Supabase, AWS) live only in `.env` locally and `/etc/ronbrowser/ron.env` on the VPS; `deploy/ron.env.example` has placeholders. Never sync `.env` (`deploy/sync-to-vps.sh` excludes it).
- `endpoints/articles.py` is SSRF-guarded: public HTTPS only, `MAX_BYTES = 2_000_000`, extracted content prefixed as untrusted.
- Projects API uses Supabase RLS with bearer tokens; guest workspaces use an `x-ron-workspace` 64-hex header hashed (sha256 → uuid5) into an identity, persisted in local SQLite (`guest_projects.py`).
- Electron IPC handlers validate the sender origin (`validateIpcSender`); the renderer window is sandboxed and automation is reachable only via localhost MCP servers.
- Core agent tools (`shell`, `editor`, `http_request`) execute on the host with no sandbox — treat agent output as trusted code execution.
- On the VPS only SSH is public; the API binds `127.0.0.1:8765` and tunnel listeners stay on loopback. Chromium's sandbox stays enabled on the server (setuid chrome-sandbox via the two sudoers rules written by `vps-bootstrap.sh`).

## Deployment

`deploy/` holds the 24/7 VPS layout; see `docs/deploy-vps.md`.

```bash
RON_VPS_HOST=<host> bash deploy/sync-to-vps.sh            # rsync repo + ../electron-playwright-mcp to /opt/ron (never .env)
ssh ron@<host> bash /opt/ron/RonBrowserRebuild/deploy/vps-install.sh   # venv, pins, npm builds, chrome-sandbox bit
RON_VPS_HOST=<host> bash deploy/local/install-tunnel.sh    # launchd SSH tunnel on this Mac
SUPABASE_DB_URL=postgresql://... bash deploy/apply-migrations.sh [--dry-run]   # pending supabase/migrations/*.sql, ledger public.ron_migrations
```

- **A backend change is not done until it is on the VPS**: `sync-to-vps.sh`, `sudo systemctl restart ron-api`, then confirm through the tunnel (`curl localhost:8765/health`, a `/bidi` `ready` frame). `npm run electron:dev` talks to the VPS, so local-only changes are invisible to the app. Schema changes need `deploy/apply-migrations.sh` with `SUPABASE_DB_URL` (direct Postgres; the REST API cannot run DDL) — it records applied files in `public.ron_migrations` and skips migrations whose first table already exists. The ledger has RLS on and no `anon`/`authenticated` grants (`017_ron_migrations_lockdown.sql`; the script re-applies that on every run), so it is invisible to the Data API.

- `deploy/vps-bootstrap.sh` — idempotent root bootstrap (Ubuntu; firewall opens only SSH; seeds placeholder env).
- systemd units (`deploy/systemd/`): `ron-api.service` (FastAPI on `127.0.0.1:8765` via `API_HOST`/`API_PORT`) and `ron-browser.service` (headless Electron under `xvfb-run`).
- The Mac tunnel (`deploy/local/tunnel.sh`): `-L 8765` brings the VPS agent API to `localhost:8765`; `-R 13000/18931/19222` exposes this Mac's Electron to the VPS as the `user` browser target. **`npm run electron:dev` expects this tunnel for normal agent work** (HF memory, 24/7 backend). It never kills `ssh` on 8765; it clears stale local Python on 8766 and Electron ports 3000/8931/9222 before starting. **Tunnel failure mode**: if this Mac's side dies without a FIN (sleep, network change), the VPS `sshd` keeps the old session's `-R` listeners for ~6 min (`ClientAliveInterval 120 × 3`); with `ExitOnForwardFailure` every launchd retry then logs `remote port forwarding failed for listen port 13000` and **nothing listens on 8765**, so every agent, Live, search and the cloud-browser picker fail at once. `tunnel.sh` now runs a pre-flight that `sudo kill`s the sshd holding 13000/18931/19222 before connecting; manual recovery is `launchctl kickstart -k gui/$(id -u)/com.ronbrowser.tunnel`, log at `~/Library/Logs/ronbrowser-tunnel.log`. **Split-port failure mode (2026-10-21)**: a local dev API that grabs `127.0.0.1:8765` while the tunnel is down (e.g. `npm run dev` during a network blip) keeps it; the reconnecting tunnel logs `bind [127.0.0.1]:8765: Address already in use` and binds **only `[::1]:8765`**, so `localhost:8765` is two backends — panel answers twice (`/chat` on one, `/sessions`/`events` replay on the other), `/bidi` lands on the keyless local Python and never sends `ready`, Discover reports Brave `not_configured`. **8765 is the tunnel's by policy, not first-come**: when `com.ronbrowser.tunnel` is loaded in launchd, `resolve-dev-api-port.sh` and `electron-dev.sh` always put the local API on 8766 (and route the UI there when the tunnel is down), and `tunnel.sh`'s Mac-side pre-flight evicts this repo's `agent/api/main.py` from 8765 (argv + physical cwd match) and refuses to start over any other process. Diagnose with `lsof -nP -iTCP:8765 -sTCP:LISTEN`: the only acceptable owner is one `ssh` pid on both `127.0.0.1` and `[::1]`.
